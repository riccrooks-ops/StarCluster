# Checkpoint 77 Validation Tiers

## Must always run

Checkpoint 77 is an architecture/documentation/runtime scrub, so the normal release path is deliberately deterministic. It must run repository and native-dependency validation, warning-as-error build and unit tests, accepted deterministic moving-missile scenarios, TL1 Phase A/B, the 35-Space construction envelope, deterministic Sensor/EW foundation, resource-semantics locks, and ScenarioRunner self-tests.

The Core tests must enforce the current degraded-fire ownership boundary: the weapon profile owns permission only; the Tactical Computer owns the penalty; both are required for Approximate-track ship-target direct fire; Firm fire remains unaffected; and main-weapon missile interception remains Firm-only. The current TL1 Tactical Computer architecture value is -25 percentage points, while no production weapon is automatically granted the capability.

The repository contract must also confirm the active Concept/documentation cleanup, missile volume-saturation wording, current source/calibration READMEs, current design-authority index, synchronized AI/calibration architecture notes, historical README archives, and absence of stale checkpoint presentation labels in the Godot host. Frozen historical output labels may remain only when they are explicitly marked as compatibility contracts.

Normal CP77 performs no Monte Carlo trials because it changes ownership/plumbing and documentation rather than a numerical combat value. CP76 remains the accepted operational evidence for -25 versus ECCM.

## Deep Calibration

Deep Calibration remains opt-in and dependency-driven. The retained long stochastic suite is available if native deterministic acceptance reveals a behavior change, but CP77 does not require it merely because historical studies exist.
